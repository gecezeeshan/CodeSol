Auto Scaling Groups (ASG) Explained

As applications grow, traffic rarely stays constant. Some days are quiet, while others experience sudden spikes. Auto Scaling Groups help manage these changes automatically without manual intervention.

An Auto Scaling Group is an AWS service that automatically adjusts the number of EC2 instances running in response to demand. Instead of managing servers one by one, scaling is handled as a group.

The goal of an Auto Scaling Group is simple: keep the right number of servers running at all times.

Why Auto Scaling Groups Exist

Manually adding or removing servers does not scale well in real-world systems. Traffic spikes can happen suddenly, servers can fail, and demand can drop without warning.

Auto Scaling Groups solve this by continuously monitoring the system and reacting automatically. When demand increases, new instances are launched. When demand decreases, extra instances are removed.

How Auto Scaling Works

Auto Scaling Groups work using a few core concepts:

  • Launch Template – defines how new EC2 instances should be created
  • Minimum capacity – the least number of instances that must always be running
  • Desired capacity – the normal number of instances to maintain
  • Maximum capacity – the highest number of instances allowed

AWS automatically ensures the desired capacity is maintained, replacing unhealthy instances when needed.

Scaling Policies

Auto Scaling Groups use scaling policies to decide when to add or remove instances. These policies are usually based on metrics such as CPU usage, request count, or custom CloudWatch metrics.

  • Scale out – add instances when load increases
  • Scale in – remove instances when load decreases

This ensures applications can handle traffic efficiently without over-provisioning resources.

Health Checks and Self-Healing

Auto Scaling Groups continuously perform health checks on instances. If an instance becomes unhealthy, it is automatically terminated and replaced with a new one.

This self-healing behavior improves reliability and reduces downtime without manual effort.

Common Use Cases

  • Web applications with fluctuating traffic
  • APIs behind an Application Load Balancer
  • Microservices running on EC2
  • Systems requiring high availability

Final Thoughts

Auto Scaling Groups remove the need to constantly watch server load and react manually. By automatically adjusting capacity and replacing unhealthy instances, they form a critical building block for scalable and resilient architectures on AWS.

Auto Scaling Groups – Actual Configuration Steps (AWS Console)

This section explains how to create and configure an Auto Scaling Group (ASG) from scratch using the AWS Management Console.

Step 1: Prepare a Launch Template (Required)

Auto Scaling Groups do not launch instances directly. Instead, they rely on a Launch Template that defines how EC2 instances should be created.

  • Open EC2 → Launch Templates
  • Click Create launch template

Provide the following details:

  • Template name (e.g., web-app-template)
  • AMI (Amazon Linux 2023 or Ubuntu 22.04)
  • Instance type (e.g., t3.micro)
  • Key pair (for SSH access)
  • Security group (allow HTTP/HTTPS, restrict SSH)
  • (Optional) User Data to install software (Nginx, app startup script)

Click Create launch template.

✔ This template will be reused every time Auto Scaling launches a new instance.

Step 2: Create the Auto Scaling Group

  • Open EC2 → Auto Scaling Groups
  • Click Create Auto Scaling group
  • Enter a name (e.g., web-app-asg)
  • Select the previously created Launch Template

Click Next.

Step 3: Choose Network and Subnets

  • Select the VPC
  • Choose multiple subnets (at least 2 in different Availability Zones)
✔ This enables high availability by distributing instances across zones.

Step 4: Attach Load Balancer (Recommended)

  • Select Attach to an existing load balancer
  • Choose Application Load Balancer (ALB)
  • Select a target group (HTTP / HTTPS)
  • Enable Elastic Load Balancing health checks

✔ Traffic is distributed automatically and unhealthy instances are replaced.

Step 5: Configure Group Size

  • Minimum capacity: 1
  • Desired capacity: 2
  • Maximum capacity: 4
  • Minimum ensures availability
  • Desired represents normal operation
  • Maximum prevents runaway scaling and cost spikes

Step 6: Configure Scaling Policies

Option 1: Target Tracking (Recommended)

Choose a Target tracking scaling policy and select Average CPU utilization.

Example target value: 50%

✔ AWS automatically adds or removes instances to maintain this level.

Option 2: Step Scaling (Advanced)
  • CPU > 70% → add 1 instance
  • CPU < 30% → remove 1 instance

Target tracking is sufficient for most workloads.

Step 7: Enable Health Checks

  • Health check type: EC2 or ELB (recommended)
  • Health check grace period: e.g., 300 seconds
✔ This allows instances time to start before evaluation.

Step 8: Review and Create

  • Review all configuration settings
  • Click Create Auto Scaling Group

Auto Scaling is now active.

What Happens After Creation?

  • Instances launch to meet desired capacity
  • Instances are distributed across Availability Zones
  • Failed instances are replaced automatically
  • Scaling occurs based on traffic without manual intervention

Common Real-World Setup (Example)

  • Instance type: t3.micro
  • Min / Desired / Max: 1 / 2 / 4
  • Load balancer: Application Load Balancer
  • Scaling metric: CPU 50%
  • Health check: ELB

Common Mistakes to Avoid

  • Using only one subnet
  • Forgetting to attach a load balancer
  • Allowing SSH from 0.0.0.0/0
  • Setting maximum capacity too high
  • Not configuring a health check grace period
