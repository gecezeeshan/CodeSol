ALB vs NLB: When Each Matters (With Configuration Steps)

AWS provides multiple load balancers, but in real projects the choice usually comes down to Application Load Balancer (ALB) or Network Load Balancer (NLB). They solve different problems and are configured differently.

When to Use ALB vs NLB (Quick Context)

Use ALB when:
  • Traffic is HTTP or HTTPS
  • Routing decisions depend on URL paths or hostnames
  • Applications are web-based or API-based
  • You need features like authentication, redirects, or WAF
Use NLB when:
  • Traffic is TCP, UDP, or TLS
  • Ultra-low latency and high throughput are required
  • You need to preserve the client IP address
  • You are handling non-HTTP protocols

Application Load Balancer (ALB) – Configuration Steps

ALB operates at Layer 7 (Application Layer).

Step 1: Create a Target Group
  • Go to EC2 → Target Groups
  • Click Create target group
  • Target type: Instance (or IP / Lambda if required)
  • Protocol: HTTP
  • Port: 80
  • Select the VPC
  • Health check path: /
Step 2: Create the Application Load Balancer
  • Go to EC2 → Load Balancers
  • Click Create load balancer
  • Select Application Load Balancer
  • Name: web-alb
  • Scheme: Internet-facing
  • IP address type: IPv4
  • Select at least two subnets in different AZs
  • Security group: Allow HTTP (80) / HTTPS (443)
Step 3: Configure Listener Rules
  • Listener protocol: HTTP
  • Port: 80
  • Forward traffic to the target group
  • Optional: Path-based routing (/api, /images)
  • Optional: Host-based routing (api.example.com)
Step 4: Attach ALB to Auto Scaling Group
  • Open Auto Scaling Groups
  • Select your ASG
  • Edit Load balancing
  • Attach the ALB target group

✔ ALB now distributes HTTP traffic and replaces unhealthy instances automatically.

Network Load Balancer (NLB) – Configuration Steps

NLB operates at Layer 4 (Transport Layer) and is optimized for performance.

Step 1: Create a Target Group
  • Target type: Instance
  • Protocol: TCP
  • Port: 80 (or application port)
  • Health check protocol: TCP
Step 2: Create the Network Load Balancer
  • Name: tcp-nlb
  • Scheme: Internet-facing or Internal
  • IP address type: IPv4
  • Select one subnet per AZ
  • Optional: Assign Elastic IPs for static IPs
Step 3: Configure Listener
  • Protocol: TCP
  • Port: 80
  • Forward traffic to the target group

✔ NLB starts routing traffic immediately with minimal latency.

Step 4: Attach NLB to Auto Scaling Group
  • Select the ASG
  • Edit Load balancing
  • Attach the NLB target group

Key Configuration Differences

  • OSI Layer: ALB (Layer 7) | NLB (Layer 4)
  • Protocols: HTTP/HTTPS | TCP/UDP/TLS
  • Routing: Path & Host based | None
  • Security Groups: ALB – Yes | NLB – No
  • Static IP: ALB – No | NLB – Yes
  • Latency: ALB – Low | NLB – Ultra-low
  • Client IP: Headers | Native

Common Real-World Patterns

  • ALB + ASG → Web applications and APIs
  • NLB + ASG → Databases, messaging systems, custom TCP services
  • CloudFront → ALB → Global web traffic
  • NLB → ALB → Advanced hybrid setups

Common Mistakes to Avoid

  • Using NLB for HTTP routing
  • Using ALB for non-HTTP protocols
  • Forgetting to attach target groups to Auto Scaling Groups
  • Using only one subnet (no high availability)
  • Skipping health check configuration

ALB and NLB are not competitors; they are tools designed for different layers of the network stack. Choosing the right one depends on protocol requirements, routing needs, performance goals, and overall architecture.

Understanding these differences helps build systems that are both scalable and efficient.
